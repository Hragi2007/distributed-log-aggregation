Distributed Log Aggregation with SDN Prioritisation

Project 10 · PES University · Goutami Velaga, Jahnavi S, Harshith Ragi

Under a 12 Mbps congestion load, critical logs averaged about 6 ms with the controller, against about 459 ms without it. Every other severity took about 455 ms in both runs. No logs were lost in either run.

Topology

Packets from the three clients (dots) flow through s1 and across the bottleneck to h4. Critical packets (green) go to queue 1 when the controller is running. The bottleneck flashes because it is the congested link.

Run it yourself

Each command has a copy button. Run them in the order shown, in the terminals described. The first command in each group should be done once per session.

1. Setup (once)

Get the latest code and clear any old Mininet state. Only do this before starting Ryu.

cd ~/distributed-log-aggregation && git pull
sudo mn -c

2. Start the controller (Terminal 1)

Start Ryu, which decides how the switches prioritise critical logs. Leave this terminal running. Never run sudo mn -c while it runs, because it stops Ryu.

cd ~/distributed-log-aggregation && source ~/ryu-venv/bin/activate && ryu-manager sdn-controller/my_controller.py

3. Start the network with the controller (Terminal 2)

Build the 4-host, 2-switch topology with the QoS queues on the bottleneck. Ryu should print "Switch connected" twice.

sudo python3 mininet/topology.py
sh ovs-vsctl list qos

The second command confirms the queues exist.

4. Start the servers on h4 (inside the Mininet prompt)

Start the iperf server, which receives the background load, and the log server, which collects the logs and writes the report.

h4 iperf -s -u -p 5001 &
h4 python3 udp-app/log_server.py --idle-exit 10 --out results/final_sdn > results/server_final_sdn.txt 2>&1 &

5. Create congestion and send the logs (inside the Mininet prompt)

Start a 12 Mbps UDP load from h1 to fill the 10 Mbps link, then send the logs from all three clients at once. Run the clients in one line so they start together.

h1 iperf -c 10.0.0.4 -u -p 5001 -b 12M -t 60 &
py [h.cmd('python3 udp-app/log_client.py --server 10.0.0.4 --name=%s --count 1500 --rate 50 > /dev/null 2>&1 &' % h.name) for h in (h1, h2, h3)]

Wait about 40 seconds, then show the report.

h4 cat results/server_final_sdn.txt

6. Measure latency under the same load (inside the Mininet prompt)

Send pings from h2 with each traffic type while the load runs. Start the load in step 5 first, and run these within the 60 seconds.

h2 ping -Q 0xb8 -c 30 -i 0.2 10.0.0.4
h2 ping -Q 0x68 -c 30 -i 0.2 10.0.0.4
h2 ping -c 30 -i 0.2 10.0.0.4

The first is critical, the second is error, and the third is default.

7. Check the rules and queues (inside the Mininet prompt)

Show that the controller installed the priority rule for critical traffic, and that queue 1 received the critical packets.

sh ovs-ofctl -O OpenFlow13 dump-flows s1 | grep nw_tos=184
sh ovs-ofctl -O OpenFlow13 queue-stats s1

8. Baseline: same test without the controller (Terminal 2)

Stop Ryu first (Ctrl+C in Terminal 1). Then restart the network without the controller, so the switches forward on their own. Use a new output folder, so old data isn't mixed in.

exit
sudo mn -c
sudo python3 mininet/topology_standalone.py

Then repeat steps 4 to 5 inside the Mininet prompt, with this server command:

h4 python3 udp-app/log_server.py --idle-exit 10 --out results/baseline_clean > results/server_baseline_clean.txt 2>&1 &

Wait about 60 seconds, then show the report.

h4 cat results/server_baseline_clean.txt

Run each command once. Repeating the client line starts extra clients and changes the results.

Scope and Notes

  • The controller and baseline runs use the same topology, QoS queues, 12 Mbps iperf load and log clients (1,500 logs per host at 50 logs/s). The only difference is the controller.
  • Everything runs as Mininet emulation on one VM, so delay values describe this setup and can vary slightly between runs.
  • h2's critical logs averaged 18.7 ms, higher than h1 and h3 (about 0.3 ms), because h2 also sent the ping tests during the run.
